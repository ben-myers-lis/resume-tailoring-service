STAGE: PROMPT MAINTENANCE
This task changes the reusable package, not the candidate facts or resume. Apply the current core policy. Inputs: current package version and relevant files, actual assessment feedback and source/date, original request and draft when available, explicit user decisions, and regression cases. Output: a complete proposed replacement for each affected file plus a change log and regression results/limits.

1. Read the actual feedback. If an attachment is unavailable, state the limitation and proceed from sufficient written feedback. Do not claim to inspect inaccessible content.
2. Classify each issue: evidence/factual, technical/causal, business context, skills breadth, outcome/measurement, JD interpretation, emphasis/readability/layout, or workflow/delivery. Separate universal lessons from candidate-specific facts.
3. Map it to a current policy/rubric check. Mark accepted and generalized, already covered but needing enforcement, case-specific, or not adopted with a reason. Distinguish verified errors from uncertain assertions and missing detail.
4. Make the smallest consistent change. Update core policy, stage prompt, input/output schema, reference selection, validator, and regression cases where affected. Replace contradictions instead of appending competing instructions. Preserve accepted fresh-start, evidence/mode, chronology, breadth, metrics, emphasis, layout, and no-interruption rules.
5. Keep the keyword catalog a vocabulary reference. Add new terms only with appropriate category/provenance; do not turn a specific employer's stack into everyone's required experience. Assessment advice cannot create personal facts or authorize hypothetical metrics.
6. Test sparse APPLICATION evidence, narrow genuine stacks, explicit illustrative metrics, new JD after illustrative work, compound tenure requirements, alternatives, narrow revision scope, chronology uncertainty, and complete audit/lineage. Distinguish deterministic tests, human review, and actual live-model evaluations.
7. Return package version, source/date, finding -> rule/enforcement change -> files -> rationale, all changed content, remaining questions, and test results. The host selects when a tested version becomes active; do not change production instructions or schedule future runs automatically.
